# Cheepfud Backend — Project State

Last updated: 2026-09-10, after extending the checkout lock to cover the whole payment attempt (closing the sequential-double-checkout gap). Next up: see TASKS.md.

## Stack (already installed, don't reinstall)

Node/Express/TypeScript, MongoDB Atlas + Mongoose, Redis (ioredis), Brevo (email), Cloudinary + Multer (uploads), JWT (jsonwebtoken) + bcryptjs, express-validator, express-rate-limit, Scalar (`/docs`) + hand-maintained OpenAPI in `src/docs/openapi.ts`. Deployed on Render (staging + production, both live and working).

## Architecture

Strict layering per BACKEND_RULES.md: Controller (HTTP only) → Service (business logic) → Repository (DB only) → Integrations (external providers, behind contract interfaces in `src/integrations/contracts/`). DI via `src/services/service-container.ts` — every service/repository/store instance is constructed once there and imported by controllers, not `new`'d ad hoc.

## Data model — User (`src/models/user.model.ts`)

Fields: `email`, `firstName`, `lastName`, `phoneNumber`, `organizationName`, `organizationType`, `description` (Phase 18, org "what we do"/mission text, optional, see below), `password` (select:false, bcrypt-hashed via pre-save hook, 12 rounds), `passwordChangedAt`, `accountType`, `role`, `verificationStatus`, `onboardingStatus`, `isEmailVerified`, `isActive`, `deliveryAddresses` (Phase 10, see below).

**Enums** (`src/types/enums.ts`):

- `UserRole`: `user | admin | organization | fso`
- `AccountType`: `individual | organization` — what the user picks at signup, drives which onboarding endpoint runs. `role` is derived from it (individual → `user`, organization → `organization`), not the same field.
- `OrganizationType`: `farmer | vendor | ngo | foundation | religious_body | agency` — only set for `role: organization`. Determines document category (see below): `farmer`/`vendor` = supply-side, the rest = campaign-side.
- `VerificationStatus`: `pending | under_review | verified | rejected`
- `OnboardingStatus`: `not_started | account_type_selected | completed`

**Critical distinction, don't conflate these two fields:**

- `isEmailVerified` — set true by OTP verification. Nothing else.
- `verificationStatus` — org admin-approval status. For `role: user`, set to `verified` immediately when individual onboarding completes (no review needed). For `role: organization`, stays `pending` after onboarding, moves to `under_review` after document upload, and `verified`/`rejected` only via admin review.

Model also has `comparePassword()`, `changedPasswordAfter(jwtTimestamp)` (invalidates JWTs issued before a password change), and a `toJSON` transform that strips `password`/`passwordChangedAt` from every response automatically.

**Flagged discrepancy found during Phase 10 (not fixed — needs a decision, not a silent change):** the `pre(/^find/)` hook that's supposed to auto-exclude `isActive: false` users from all queries is present in `user.model.ts` but **commented out**. `protect` middleware still checks `user.isActive` explicitly after `findById`, so deactivated users can't authenticate — but every *other* `UserModel.find*` call in the codebase (e.g. `findByEmail`, `findOrganizations`) currently returns deactivated users too, contradicting this doc's prior claim. Flagging rather than re-enabling it myself since that would change query behavior for every existing caller.

## Auth flow (fully built, tested end-to-end on staging)

- **Onboarding:** `POST /v1/otp/request` (auto-creates user by email) → `POST /v1/otp/verify` (sets `isEmailVerified`) → `POST /v1/onboarding/account-type` (sets `accountType` + derives `role`) → `POST /v1/onboarding/individual` or `/v1/onboarding/organization` (collects profile fields + password, sets final `verificationStatus`).
- **Login/session:** `POST /v1/auth/login`, `POST /v1/auth/refresh`, `POST /v1/auth/logout`, `GET /v1/auth/me`. Access token: short-lived JWT (15m), stateless verification. Refresh token: longer-lived (7d), tracked in Redis by `jti` (hashed, not raw), **rotated on every use** (old one deleted, `refresh:user:{userId}` set tracks all of a user's active jti's for bulk revocation). Logout blacklists the access token's hash in Redis until its natural expiry.
- **`protect` middleware** (`src/middleware/protect.middleware.ts`): checks blacklist → verifies JWT → loads user → checks `isActive` → checks `changedPasswordAfter`. Populates `req.user = { id, role, verificationStatus }` and `req.token`.
- **Password recovery:** `POST /v1/auth/forgot-password` (OTP to email, generic response regardless of whether the email exists — no enumeration), `POST /v1/auth/reset-password` (OTP + new password, revokes ALL refresh tokens for that user), `POST /v1/auth/change-password` (authenticated, current password required, revokes all OTHER sessions but issues a fresh pair so the current session survives).
- **OTP service is purpose-aware** (`src/services/otp.services.ts`): `OtpPurpose = 'email_verification' | 'password_reset'`, separate Redis keys per purpose. Resend cooldown enforced via a separate `otp:cooldown:{purpose}:{email}` Redis key (`OTP_RESEND_COOLDOWN_SECONDS` env var) — applies uniformly to `/otp/request` and `/auth/forgot-password`.
- **Auth-related error codes** are in `src/errors/error-codes.ts` — check there before adding new ones, most auth/validation cases are already covered.

## Organization verification (fully built, tested end-to-end)

- `requireVerifiedOrganization` (`src/middleware/verification.middleware.ts`): blocks any route it's attached to for `role: organization` users whose `verificationStatus !== verified`. Passes through untouched for `user`/`admin`/`fso`. **Only checks role + status — does NOT distinguish farmer/vendor from NGO/foundation.** If a route needs to be supply-side-only or campaign-side-only, that's a separate check to add (not built yet — needed for Phase 8).
- `requireRole(...roles)` (`src/middleware/role.middleware.ts`): generic role gate, used for `/v1/admin/*` (`requireRole(UserRole.ADMIN)`).
- **Document catalog** (`src/config/document-catalog.ts`): 5 document types per category (`supply` vs `campaign`, derived from `organizationType` via `getOrgDocumentCategory()`), 3 mandatory + 2 optional each. Placeholder Nigerian-market names — will be revised once the co-founder sends the real list, but the mechanism (mandatory-coverage check) shouldn't need to change, only the catalog data.
- `POST /v1/organizations/documents`: multipart upload, `documents` (files) + `documentTypes` (parallel array, same order) fields. **All mandatory types for the org's category must be included in one submission** — not accumulated across multiple calls. Validates types against the catalog, uploads to Cloudinary (`cheepfud/verification-documents` folder), stores `VerificationDocument` records, flips `verificationStatus` to `under_review`.
- `GET /v1/organizations/document-catalog` — returns the catalog entries for the logged-in org's category (frontend uses this to know what to ask for).
- `GET /v1/organizations/verification-status` — org checks their own status + submitted docs.
- `GET /v1/organizations/dashboard` — placeholder endpoint, exists only to prove `requireVerifiedOrganization` works end-to-end. Not a real feature — expect it to be replaced/removed once real org-only endpoints exist (e.g. product creation in Phase 8).
- **Admin review** (`/v1/admin/organizations*`, `requireRole(admin)` on the whole router): `GET /organizations` (filter by `status` query param), `GET /organizations/:id` (detail + documents), `PUT /organizations/:id/verify` (`{ decision: 'approved'|'rejected', rejectionReason? }`, required when rejecting). Sends a Brevo email on either decision, and (since the rejectionReason bug fix below) also persists it. There is currently **no self-service way to become admin** — that's set manually in the DB for now, intentionally, since it shouldn't be public.

**Decision changes are always allowed, deliberately (2026-09-08):** `PUT /v1/admin/organizations/:id/verify` has **no** "already reviewed"/"already verified" guard — unlike Products/Campaigns, which block re-moderation once a decision is made, admin can change an organization's verification decision at any time, in either direction, as a deliberate correction/override capability (distinct from — and not a substitute for — an org's own resubmission flow, which still doesn't exist). A guard (`verificationStatus === VERIFIED → 409`) existed before this and was removed; it only ever blocked touching an already-verified org, re-review of a rejected org already worked. The same notification email fires on every call, including corrections, and `rejectionReason` clears (via the fix below) whenever the decision becomes `approved`, regardless of how many times the decision has flipped. **Not yet done:** the admin web dashboard (separate repo) still needs its Organizations review drawer updated to show the decision footer outside the Pending/Under Review tabs and label a correction distinctly from a first-time review — tracked in that repo's own backlog, not here.

**Bug fix — organization `rejectionReason` now persisted (2026-09-08):** `PUT /v1/admin/organizations/:id/verify` required `rejectionReason` when rejecting and emailed it, but never stored it anywhere retrievable — mobile testing caught this. `User.rejectionReason` (optional string, same field name/pattern as `Product.rejectionReason` from Phase 19) is now set on reject and explicitly cleared to `null` (not `undefined` — ambiguous across Mongo driver versions in update payloads) on a later approval, so a stale reason never survives a subsequent approval. `GET /v1/admin/organizations/:id` picked this up automatically (it returns the full `User` document), but `GET /v1/organizations/verification-status` did **not** — `DocumentService.getVerificationStatus` builds a hand-constructed response object, not the full document, so it needed an explicit one-line addition. Worth remembering: a new `User` field flowing through "automatically" is only true for endpoints that return the full document — any endpoint building a custom projection needs the field added by hand, every time.

**Organization description/mission field (Phase 18):** `User.description` — optional String, trimmed, max 1000 chars (enforced at the validator level, not schema `maxlength`, for a clearer error message — same "business-rule limits live outside the schema" pattern as `deliveryAddresses`' max-5 rule). Accepted on `POST /v1/onboarding/organization` only; conceptually organization-only but no schema discriminator, same as `organizationName`/`organizationType`. Flows through automatically everywhere organization data is already returned (admin org list/detail, the onboarding response itself) since it's just a new field on the existing `User` document — verified via a real end-to-end HTTP test, not just assumed. **Explicitly not built:** there is still no endpoint to edit an organization's profile (including this field) after onboarding completes — the role-navigation doc's "Organization Profile" settings screen implies one should exist eventually, but nothing like it has been built yet. Don't assume it exists when scoping future frontend work against this field.

**Product Moderation (Phase 19, fully built, tested end-to-end against staging Mongo+Redis):** closes the pre-launch gap where `isApproved` was hardcoded `true` at creation since Phase 8 — every verified farmer/vendor's listing went straight to public visibility with zero review.

Single source of truth, no derived/synced boolean kept alongside it (same anti-pattern this project has already been burned by twice — `accountType`/`role`, `isEmailVerified`/`verificationStatus`). Flagged for whenever that flow gets scoped, not silently assumed to exist.

## Cart (fully built, tested end-to-end against staging Mongo+Redis)

- `Cart` model (`src/models/cart.model.ts`): one document per user (`user` ref is `unique`), `items: [{ product, quantity }]`. **Decision: no display-field snapshot on cart items** (name/price/image) — `GET /cart` always populates the live product anyway (to compute subtotal and flag unavailable items), so a snapshot would be write-time complexity with nothing ever reading it. `unitPrice`/subtotal/total are never stored — always computed at read time from the live `Product.price`, so a price change is reflected immediately and nobody can lock in a stale cheap price.
- `expiresAt`: absolute-expiry TTL (`cartSchema.index({ expiresAt: 1 }, { expireAfterSeconds: 0 })` — Mongo deletes the doc once that date is in the past), set to `now + 7 days` on every mutation (add/update/remove/clear), _not_ refreshed on reads.
- `CartRepository.upsertItem` sets an item to an already-computed final quantity (creating the cart and/or item entry if needed) — the increment math (existing qty + requested, capped/validated against `quantityAvailable`) happens in `CartService`, not the repository, per the "no business rules in repositories" rule.
- Stock/floor rules in `CartService.addItem`: `minimumOrder` is only enforced on a product's _first_ add to the cart (not on top-ups of an existing line); `quantityAvailable` is enforced as a hard ceiling on every add — a request that would exceed it is rejected with `VALIDATION_ERROR`, never silently truncated.
- `PUT /v1/cart/update` (`CartService.setItemQuantity`) enforces both the `quantityAvailable` ceiling and the `minimumOrder` floor — a quantity below `minimumOrder` is rejected with `400 VALIDATION_ERROR` (2026-09-09, see the "Close the Remaining Gaps" note below; this replaces an earlier documented decision that the floor wasn't re-enforced here). `quantity: 0` routes to the same remove path as `DELETE /v1/cart/:productId`, unaffected by the floor check (an explicit 0 is still "remove," not an invalid quantity to reject).
- Cart items whose product has gone `isActive: false` / `isApproved: false` (Phase 8 soft-delete) are still returned in `GET /cart` with `unavailable: true` and `lineTotal: 0`, and excluded from `subtotal`/`totalItems` — never silently dropped.
- `DELETE /v1/cart/:productId` and `DELETE /v1/cart` (clear) both leave the (possibly empty) cart document in place rather than deleting it, so "cart was cleared" and "user never had a cart" look identical to `GET /cart` (both return the same empty shape: `{ items: [], subtotal: 0, totalItems: 0 }`).
- All 5 routes (`POST /v1/cart/add`, `GET /v1/cart`, `PUT /v1/cart/update`, `DELETE /v1/cart/:productId`, `DELETE /v1/cart`) require only `protect` — no role restriction, any authenticated account (individual or organization) can have a cart. Always the caller's own cart via `req.user.id`; there is no `:userId` param anywhere in this domain.
- No new `ErrorCode`s were needed — "product not in cart" reuses the generic `NOT_FOUND`, over-stock/under-minimum reuse `VALIDATION_ERROR`, unpurchasable product reuses Phase 8's `PRODUCT_NOT_FOUND`.
- A legacy reference implementation (old learning-project code, controllers-with-DB-logic style) was used for scope context only — not mirrored architecturally.

**Addendum (Phase 9.5) — `PATCH /v1/cart/increment`, the ±1 stepper endpoint:**

- `CartRepository.incrementItemQuantity(userId, productId, delta)` uses an atomic MongoDB `$inc` on `items.$.quantity`, not a read-then-`$set`. This is a deliberate deviation from a literal "read current quantity then call the same update as PUT /cart/update" implementation: a read-then-write can lose an update under concurrent requests (two racing +1's can both read the same starting value and collapse into a single +1), which is exactly what Phase 9.5's own test suite checks for. `$inc` is atomic per-document in MongoDB, so concurrent increments always serialize correctly.
- The `quantityAvailable` ceiling can't be checked as part of that same atomic op (it lives on the `Product` document, a different collection/no multi-document transaction in use anywhere in this codebase). `CartService.adjustQuantity` instead applies the increment optimistically, then validates the resulting quantity and — if it's invalid (exceeds stock, or the product is no longer purchasable) — rolls it back with a compensating `-delta` `$inc` before throwing. `newQuantity <= 0` after the increment is treated as removal, delegating to the same `removeItem` used elsewhere.
- `setItemQuantity` (PUT /cart/update) and the increment path share the ceiling-check/removal logic via a private `applyQuantity` helper — `setItemQuantity` calls it directly (its own read-then-`$set` is fine there since PUT sets an absolute value, not a relative delta, so there's no lost-update risk to begin with); `adjustQuantity` reaches the same rules after its atomic increment lands.
- `delta` must be exactly `1` or `-1` — validated in both `cart.validator.ts` (route boundary) and `CartService.adjustQuantity` (defense in depth, same pattern as the rest of this codebase). This is not a general "add N" endpoint; `POST /v1/cart/add` remains that.
- Tested for real, including firing two increment requests concurrently via `Promise.all` against staging and confirming the final quantity reflects both increments (no lost update).

**Bug report investigated, mostly didn't reproduce — checkout gap found and fixed instead (2026-09-09):** a report claimed `POST /v1/cart/add` accepted a quantity below a product's `minimumOrder` and returned `200`. Traced and empirically re-tested against staging: it doesn't reproduce — `addItem`'s first-add floor check (documented two bullets up) works correctly and rejects it with `400 VALIDATION_ERROR`. Likely the report was against a stale deployment. What IS confirmed real: `PATCH /cart/increment`'s decrement path had the exact same "no floor re-check" behavior as `PUT /cart/update` at the time — a line at exactly `minimumOrder` could be `-1`'d one below it, since both shared the same `applyQuantity` ceiling-only logic. Left unchanged at the time (flagged rather than silently altering an already-documented decision without a human call) — since resolved, see below. **What actually needed fixing then:** `OrderService.checkout()` never checked `minimumOrder` at all — a cart line sitting below the minimum (reachable via the already-legitimate PUT/PATCH paths) could proceed all the way to a real paid order. Fixed inside the existing per-checkout Mongo transaction, alongside the `isActive`/`moderationStatus` check it already had — rejects the whole checkout with `VALIDATION_ERROR` naming the product and its minimum, same "no partial order" guarantee as everything else in that transaction.

**"Close the Remaining Gaps" — PUT/PATCH asymmetry resolved, minimumOrder now visible in GET /cart (2026-09-09):** the PUT-vs-PATCH floor-enforcement asymmetry flagged in the note above has now been explicitly decided (by the human, via `TASKS.md`, not inferred): **`PUT /v1/cart/update`** now rejects an explicit below-`minimumOrder` quantity with `400 VALIDATION_ERROR` (same message pattern as `add`) — an explicit "set to this exact quantity" action treats an invalid quantity as a mistake to correct, not an intent to remove. **`PATCH /v1/cart/increment`** now removes the line entirely when a `-1` decrement would take it below `minimumOrder` (`CartService.adjustQuantity`, guarded to `delta === -1` only — an increment landing below minimum on legacy data is never treated as a removal signal) — a relative decrement crossing below the seller's minimum reads as "I don't want this small an amount," the same intent as decrementing to 0, not an error to reject. The two endpoints are now deliberately asymmetric on purpose, not by accident: PUT corrects, PATCH removes. Also added `minimumOrder` to the product object in `CartItemView`/`GET /v1/cart` (`CART_PRODUCT_POPULATE`'s `select`) — previously omitted, which is why the mobile cart-screen stepper had no way to know the real floor and defaulted to `min={1}`. Verified via an 11-assertion HTTP-level integration test against staging (PUT-below-minimum rejection + message content, PATCH-decrement-to-removal, `GET /cart` exposing `minimumOrder`, and regressions: `add`'s existing floor check, PUT/PATCH still working at-or-above the floor).

## User Addresses (fully built, tested end-to-end against staging Mongo+Redis)

First real "Users/Profile" feature beyond auth — a hard prerequisite for Phase 12 (Orders) checkout, which will let a buyer pick a saved address instead of typing one inline.

- `deliveryAddresses` is an embedded array on `User` itself (`src/models/user.model.ts`), not a separate collection/repository — `UserRepository` was extended instead of creating a new one, matching how a subdocument array on an existing model should be handled. `IDeliveryAddress` is a **plain data interface, not `extends Types.Subdocument`** — the hydrated type (with `_id`, `.deleteOne()`, etc.) comes from `Types.DocumentArray<IDeliveryAddress>`'s own default generic. Having `IDeliveryAddress` extend `Types.Subdocument` *and* wrapping it in `Types.DocumentArray` double-applies that wrapping and collapses `_id`'s type to `never` — a real TS footgun worth remembering if another embedded-subdocument-array field gets added elsewhere.
- Max 5 addresses and all `isDefault`-invariant business rules live in `UserService`, not the schema or repository — `UserRepository`'s address methods (`addAddress`, `updateAddress`, `removeAddress`, `setDefaultAddress`, `findAddresses`) are deliberately mechanical (Mongoose subdocument-array helpers + one `.save()`), per BACKEND_RULES' repository/service split.
- `NIGERIAN_STATES` (all 36 states + FCT) added to `src/utils/constants.ts` (extended, not recreated) — `state` is validated against this list, not accepted as free text.
- Business rules, all enforced server-side regardless of client input: first address added is always `isDefault: true`; `setDefaultAddress` un-defaults every other address in the same write so exactly one is ever default; removing the current default auto-promotes the **most recently added remaining address** (last element of the array — relies on `deliveryAddresses` always preserving push/insertion order, since nothing in this domain ever reorders it); removing the last address is valid and leaves an empty array, not an error.
- **Design decision:** `PUT /v1/users/addresses/:addressId` does not accept an `isDefault` field at all — only `PATCH /v1/users/addresses/:addressId/default` can change default status. Allowing `isDefault` through the general update endpoint too would risk landing two addresses marked default at once, since that endpoint doesn't run the un-default-the-rest logic.
- Address ownership is enforced structurally, not by a separate check: every repository method starts from `UserModel.findById(callerUserId)` (never a global `Address.findById`), so an `addressId` belonging to another user simply isn't found inside *this* user's array — 404, and existence for another user is never confirmed (no 403 path exists for this domain).
- No new `ErrorCode`s needed — reuses `VALIDATION_ERROR` (max addresses, invalid state/phone), `NOT_FOUND` (address not found/not owned), `USER_NOT_FOUND`.
- **Flagged discrepancy found while working in `user.model.ts`, not fixed as part of this phase:** see the note under "Data model — User" above — the `pre(/^find/)` isActive-exclusion hook this doc previously described as built is actually commented out in the code.

**Phone validation standardized (2026-09-09):** found via mobile Phase 6 — `POST /v1/users/addresses` rejected `08012345678` (the leading-`0` local format, the most natural way a Nigerian writes their own number). Investigated first: the address `phone` regex and onboarding's `phoneNumber` regex were NOT actually inconsistent with each other (both used the identical `/^\+?[1-9]\d{7,14}$/`, duplicated across two files) — the real bug was that this one shared-but-copy-pasted pattern rejected any leading-`0` input everywhere uniformly, since `[1-9]` as the first character excludes `0` by construction. Fixed by replacing both copies with one shared validator: `src/utils/phone.ts` (`isValidNigerianPhone`/`normalizeNigerianPhone`, pattern `^(?:\+?234|0)?[789]\d{9}$` — accepts local `0XXXXXXXXXX`, `+234XXXXXXXXXX`, `234XXXXXXXXXX`, and bare `XXXXXXXXXX`, all resolving to the same 10-digit subscriber number starting with 7/8/9, which covers every Nigerian mobile network prefix) plus `phoneValidationRule(field, { optional? })` in `common.validator.ts`. Normalization to the canonical `+234...` stored format happens via `.customSanitizer()` in the validator chain — the same "mutate `req.body` in place" pattern `.normalizeEmail()` already used on email fields in this codebase, so no service-layer change was needed; `validateRequest` doesn't use `matchedData()`, so the sanitized value is just already on `req.body` by the time the controller reads it. Used by `User.phoneNumber` (individual + organization onboarding) and `IDeliveryAddress.phone` (address create/update) — every phone-collecting field in the codebase, confirmed via a full-codebase grep, not just the two originally-suspected files. Verified via a 16-assertion HTTP-level integration test against staging: local format now accepted + normalized on all three call sites, previously-passing formats (`+234...`, bare `234...`, bare 10-digit) still pass and normalize to the same canonical value, genuinely invalid input (too short, contains letters) still rejected.

## Orders + Payment (Paystack) — fully built, tested end-to-end against staging Mongo+Redis+real Paystack test-mode API

The biggest phase so far — real money, so extra scrutiny went into idempotency, rollback, and never leaving state half-done. All 18 automated scenarios in TASKS.md 11.15 pass against staging (49 assertions); item 19 (a live checkout through Paystack's actual hosted UI via ngrok) is a manual step not done by an AI agent — see TASKS.md.

**Multi-vendor split:** one checkout event, one combined payment, but **one `Order` document per seller** — a cart with items from 2 sellers produces 2 `Order`s sharing a `checkoutReference`, each independently trackable via its own `orderStatus`. The single `Transaction` covers the combined total across all of them (`Transaction.amount`, `relatedOrders`). `Order.subtotal`/`deliveryFee`/`total` are always scoped to that one seller's items only — never the combined checkout total.

**Snapshot direction is the opposite of Cart, on purpose:** Cart items stay live (always priced from the current `Product.price` at read time). `Order.items[].productName`/`unitPrice`, and `Order.deliveryAddress` (copied from the chosen `User.deliveryAddresses` entry), are frozen at checkout time — an Order is a historical receipt; a later product reprice or address edit/delete must never change what a past order shows.

**Checkout (`OrderService.checkout`) — no partial state, ever:**
1. Cart items are resolved against **live** Product data — nothing from the cart or client body is trusted for pricing. Also re-checks `minimumOrder` here (2026-09-09 fix) — Cart's own floor check only applies at first-add time, and both `PUT /cart/update` and `PATCH /cart/increment` can legitimately move an existing line below it afterward (see Cart section), so checkout is the last gate before that becomes a real order.
2. Stock is decremented per line via `ProductRepository.decrementStock` (atomic `findOneAndUpdate` with a `$gte: quantity` guard — same overselling-prevention pattern as Products). If any line fails, every decrement already applied *in that attempt* is rolled back via `Promise.allSettled` (a rollback failure is logged at error level as needing manual reconciliation, not swallowed) and the whole checkout is rejected — never a partial order.
3. One `Order` per seller group is created, then `PaymentService.initializeCheckoutPayment` is called. If that throws (Paystack unreachable, etc.), **both** the stock decrements from step 2 **and** the just-created Orders are rolled back before a clean `CHECKOUT_FAILED` (502) is returned — a buyer must never be left holding orders that were never actually submitted for payment.
4. The cart is deliberately **not** cleared at checkout — only `processSuccessfulPayment` clears it, once payment is actually confirmed. Clearing early and then having payment fail would lose the buyer's cart for nothing.
- **Compensating rollback, not a Mongo transaction:** this is a deliberate choice, not an oversight — introducing multi-document ACID transactions would be the first use of that pattern anywhere in this codebase (a bigger architectural shift deserving its own deliberate rollout), and the task spec explicitly described step-by-step compensating rollback. Flagging this as the natural next hardening step for this exact flow if it ever needs to be bulletproof against a rollback-of-a-rollback failure window.

**Webhook idempotency — atomic claim, not idempotency-check-then-write:** `TransactionRepository.markCompletedIfPending`/`markFailedIfPending` use a single atomic `findOneAndUpdate({ transactionReference, status: PENDING }, { $set: { status: ... } })` rather than a separate read-then-check-then-write. This is a deliberate deviation from the TASKS.md wording ("idempotency check first... otherwise set status"), for the same reason as the Phase 9.5 Cart-increment deviation: a naive read-then-write has a real concurrent-request race (two near-simultaneous webhook deliveries for the same reference could both read `pending` before either writes), which would double-process — double order updates, double cart-clear attempts, and critically, **duplicate emails**, which TASKS.md's own test 6 explicitly checks for. The atomic version guarantees only one caller ever proceeds past the claim, regardless of how close together duplicate/concurrent deliveries arrive. As a side effect, this same guard also protects against a late/out-of-order `charge.failed` ever downgrading a transaction a `charge.success` already completed (or vice versa) — it only matches while still `pending`.
- **Amount-mismatch safety net:** after claiming a transaction as completed, `processSuccessfulPayment` cross-checks the webhook payload's `data.amount` (kobo) against `Math.round(Transaction.amount * 100)`. A mismatch is logged at error level and the orders are deliberately left unresolved (not flipped to completed) for manual review, rather than trusting the amount blindly — belt-and-braces on top of HMAC signature verification, not a replacement for it.
- Webhook flow: verify signature (raw body, `crypto.timingSafeEqual`) → 400 immediately with no processing if invalid → log to `WebhookLog` (`processedSuccessfully: false`) → respond `200` → **then** asynchronously route to `processSuccessfulPayment`/`processFailedPayment`, and finally flip `WebhookLog.processedSuccessfully` once that finishes. `express.raw({ type: 'application/json' })` is applied at the route level in `webhook.routes.ts`, and that router is mounted in `app.ts` **before** the global `express.json()` — critical ordering, since raw bytes are unavailable for signature verification once the global JSON parser has already consumed the stream.
- **New `WebhookLogRepository.updateProcessedStatus`** wasn't in the original "create, that's it for now" spec — added because `processedSuccessfully` needs *something* to flip it after async processing, or it stays at its creation-time default forever.

**Cancel / fulfillment:**
- `cancel` (buyer-only): only while `paymentStatus !== completed` (post-payment cancel is a refund scenario, explicitly out of scope this phase — rejected with a new `ORDER_ALREADY_PAID` 400 and a "contact support" message, not a generic validation error).
- `confirmDelivery` (buyer-only, from `in_transit`) and `updateStatus` (seller-only, forward-only `pending → confirmed → preparing → in_transit → delivered`, one step at a time, new `INVALID_STATUS_TRANSITION` error code) both terminate at `delivered` — **there are two valid paths to that state**: the seller's own forward chain (e.g. pickup orders, where the seller hands off directly with no separate buyer confirmation step) and the buyer's `confirmDelivery` from `in_transit` (courier-delivery case). Both set `deliveredAt`. This is a clarified interpretation of an ambiguous spec point, not a scope addition — worth knowing if pickup vs. delivery ever need genuinely different fulfillment rules later.
- `OrderRepository.restoreStockForItems` (used by both `processFailedPayment` and `cancel`) lives on `OrderRepository` per the phase spec even though it mutates `Product` documents — it duplicates the one-line `$inc` that `ProductRepository.restoreStock` also has. Deliberate: repositories in this codebase don't depend on each other, and that duplication is smaller than the alternative layering smell of `OrderRepository` importing `ProductRepository`.

**Constructor deviations from the literal spec (both are functional necessities, not scope creep):** `PaymentService` swaps the spec's `ProductRepository` dependency for `UserRepository` + `EmailProvider` — stock restoration on failure is fully handled through `OrderRepository.restoreStockForItems(order.items)`, so a raw `ProductRepository` was never actually needed, while buyer/seller email lookups and the email-sending TASKS.md itself describes require both. `TransactionRepository` also gained `markCompletedIfPending`/`markFailedIfPending` beyond the spec's `create`/`findByReference`/`updateByReference` list, for the atomicity reasons above.

**New `ErrorCode`s:** `ORDER_NOT_FOUND`, `INVALID_STATUS_TRANSITION`, `ORDER_ALREADY_PAID`, `CHECKOUT_FAILED` (502 — Paystack unreachable during checkout), `INVALID_WEBHOOK_SIGNATURE`. Stock-shortage-at-checkout reuses the existing `VALIDATION_ERROR` (consistent with how Cart's own over-stock rejection works — no new code invented for a conceptually identical case).

**Rate limiting:** new `checkoutLimiter` (10 requests / 15 min per IP) added alongside the existing `passwordLimiter` in `rateLimiter.middleware.ts` — checkout calls out to Paystack and reserves stock, so it's capped against accidental double-submission and deliberate abuse.

**OpenAPI:** webhook endpoint got a minimal doc entry under a new `Webhooks` tag (chose to document it rather than exclude it from `/docs`, for completeness/audit purposes, even though it's never called by a frontend client) — the Orders tag covers all 6 buyer/seller endpoints per spec.

**Deferred (explicitly out of scope this phase, not silently dropped):**
- **Refunds** — a post-payment cancel is Epic 5 territory; `cancel` only works pre-payment.
- **Auto-expiry of abandoned pending-payment orders** — a buyer who starts checkout and never completes payment on Paystack's page leaves an order stuck at `paymentStatus: pending` forever with stock still decremented against it. Needs a job scheduler, which doesn't exist in this codebase yet.
**Investigated (2026-09-09) — reported as "double-checkout lock appears missing," confirmed NOT a regression:** mobile fired two `POST /v1/orders/checkout` calls "back to back" and got two `201`s with two different `checkoutReference`s. Re-verified the Phase 11.5 lock fresh, empirically, against this repo's real infrastructure (see below) — it still worked exactly as designed at the time: a true concurrent double-checkout (`Promise.all`) produced one `201` + one `409 CONFLICT`, with exactly one `Order`/`checkoutReference` landing in Mongo. `RedisLock.acquire()` also failed **closed**, not open, on a Redis error (no try/catch swallowed a connection failure anywhere between `redis.set()` and the global error handler). What mobile actually hit was the "adjacent risk" this section used to flag as deferred: the lock only blocked *overlapping* requests, and two checkout calls fired *sequentially* (first one fully completes and releases the lock before the second starts) against a cart that's still non-empty were each individually legitimate at the time, and each created a real Order set. **Also notable:** this repo's `.env` and `.env.staging` hold byte-identical `MONGODB_URI`/`REDIS_URL` (same live Mongo Atlas cluster and managed Redis instance) — there is no separate "local Redis" in this setup that could have been unreachable; local and staging are the same infrastructure.

**Fixed (2026-09-10) — the "adjacent risk" above is now closed, not deferred:** the checkout lock's lifecycle was extended from "released as soon as `checkout()` returns" to "held for the whole payment attempt." New `CheckoutLockService` (`src/services/checkout-lock.service.ts`) owns the lock as a domain concept and uses the **`checkoutReference` itself as the lock's Redis value/token**, instead of a random UUID — this is what makes release-from-elsewhere safe: a webhook or a cancel for checkout A presents A's reference, so `RedisLock`'s existing compare-and-delete refuses to release a lock a *newer* checkout B has since taken (a late webhook for an abandoned checkout can never unlock a fresh one). `RedisLock.acquire()` gained an optional third `token` parameter for this (defaults to `randomUUID()`, its original behavior — every other caller unaffected). The lock is now released only by whichever of these happens first: `PaymentService.processSuccessfulPayment` (after the orders reach `paymentStatus: completed`), `PaymentService.processFailedPayment` (after stock is restored and the orders reach `cancelled`), `OrderService.cancel` (immediately, so a genuine change of mind doesn't cost the buyer a wait), or a 15-minute Redis key TTL (`CHECKOUT_LOCK_TTL_SECONDS`, deliberately well under the 30-minute `ORDER_EXPIRY_MINUTES` default, so the lock is never still held once the order itself has already auto-expired). `OrderService.checkout()` now generates `checkoutReference` up front (it doubles as the lock token) and tracks a local `retainLockForPayment` flag — `false` by default, flipped to `true` only immediately before the success return — so every failure path (empty cart, stock shortage, a Paystack-init error) still releases the lock in the outer `finally` exactly as before, never holding it past a failed attempt. Verified via 3 throwaway HTTP-level integration scripts (split across processes to stay under the pre-existing `checkoutLimiter`) covering all 4 release paths, the TTL mechanism (checked the actual Redis TTL rather than waiting 15 real minutes), and regressions (concurrent lock behavior, immediate release on failure) — 12 assertions, all passing; scripts deleted after the run.
- **Full Notification domain** — order confirmation / new-order emails are sent directly via the existing `EmailProvider`/Brevo (two new templates: `order-confirmation-email.template.ts`, `new-order-email.template.ts`), same pattern as `AdminService`'s org-verification emails. No persisted Notification model/in-app notification center — out of scope.
- **Campaign donations** — `TransactionType` only has `product_purchase` today, but the enum and the generic `Transaction` ledger shape are deliberately ready for a future `donation` type without rework.
- Image upload for `Order.proofOfDeliveryImages` — the field/shape exists on the model (matching the Cloudinary `{ url, publicId }` pattern) but no endpoint populates it yet; not part of any of the 6 endpoints this phase.

**Hardening (Phase 11.5, 2026-08-13):** three targeted gaps closed, no new endpoints, no contract change for existing callers.
- **Double-checkout guard:** `OrderService.checkout()` now acquires a Redis lock (`checkout:lock:{buyerId}`, `SET NX`, 60s TTL, token-based release so a caller can never release a lock it no longer owns) before doing anything else, and releases it in a `finally`. A second concurrent checkout for the same buyer gets an immediate `409 CONFLICT` — never queued. New reusable `RedisLock` (`src/integrations/redis/redis.lock.ts`, wired into `service-container.ts` as `checkoutLock`) — not checkout-specific, intended for reuse by any future "only one of these in flight" flow (e.g. a donation or admin-action guard).
- **Real Mongo transactions replace the manual compensating rollback** for checkout's DB-only portion: cart validation, per-item `decrementStock`, and per-seller `Order` creation now run inside one `session.withTransaction()` (`ProductRepository.findById`/`decrementStock`, `CartRepository.findByUser`, and `OrderRepository.create` all gained an optional trailing `session?: ClientSession` param for this — every other existing caller is unaffected since it's optional). The old hand-rolled "decrement then undo on shortage" loop is gone; an item-level stock shortage now just throws inside the transaction and Mongo aborts everything automatically. The Paystack call and its own compensating cleanup (delete orders, restore stock) stay exactly as Phase 11 built them, **outside** the transaction/session — a DB transaction must never stay open across an external network call.
- **Deactivated-org product visibility:** `ProductRepository.findMany` now excludes products whose seller has `isActive: false` (via an `$nin` on seller ids collected from `UserModel`, applied before pagination/count so `skip`/`limit`/`total` stay accurate — not a post-query filter). `ProductService.getProductById` populates the seller and 404s the same way as an inactive/unapproved product if the seller is deactivated.
- The dead, commented-out `pre(/^find/)` isActive-exclusion hook flagged since Phase 10 is now deleted from `user.model.ts` — the decision to leave it disabled (it would've broken admin's ability to see deactivated orgs) was already final; this only removed the misleading dead code, no behavior change.

**Order Auto-Expiry (Phase 14, 2026-08-14):** closes the "abandoned pending-payment order" gap flagged since Phase 11 — a checkout whose buyer never completes payment on Paystack's page no longer sits at `paymentStatus: pending` with stock reserved forever.
- In-process `node-cron` job (`src/jobs/order-expiry.job.ts`, started once from `server.ts` after the DB connects — not from `app.ts`, since this is a process-lifecycle concern), schedule `*/5 * * * *` (every 5 minutes, a code constant, not runtime-configurable). `ORDER_EXPIRY_MINUTES` env var, **default 30**, is the actual business tuning knob.
- `OrderService.expireStaleOrders()` (also reachable directly via `POST /v1/admin/orders/expire-stale`, admin-only, for ops + testing without waiting on a real clock — same method, no separate logic) groups stale orders by `checkoutReference` so a whole multi-seller checkout expires together, not just whichever sibling the initial query happened to touch — one Mongo transaction per `checkoutReference` group, same `session.withTransaction` pattern Phase 11.5 established for checkout. New `OrderRepository.expireIfPending` is an atomic-claim method (`findOneAndUpdate` guarded on `paymentStatus: pending`, mirroring `TransactionRepository.markCompletedIfPending`/`markFailedIfPending`'s shape) — deliberately more defensive than the task spec strictly asked for: it guards against a webhook paying the order out from under the expiry job in the gap between the job's initial read and its write, not just against two cron instances racing each other.
- Multi-instance-safe without a distributed lock, by design — `expireIfPending`'s guard means an overlapping tick on another instance just finds nothing left to claim.
- Reuses `OrderStatus.CANCELLED`, not a new `expired` status — adds `cancellationReason` (new enum: `buyer_requested | payment_expired`) instead, so the existing buyer-initiated `cancel()` and the new auto-expiry path land on the same `orderStatus` but stay distinguishable. Deliberate, to avoid the two-fields-tracking-the-same-thing drift this project has hit before (`accountType`/`role`, `isEmailVerified`/`verificationStatus`).
- The related `Transaction` (found via `checkoutReference`, which doubles as `transactionReference` for `product_purchase`) is marked `failed` via the same atomic `markFailedIfPending`, inside the same transaction as the order/stock changes.
- **Gotcha worth remembering for future tests:** Mongoose's `timestamps: true` schema option silently strips `createdAt` out of any `Model.updateOne()` `$set` — backdating a test order's `createdAt` through the ODM was a no-op; had to go through `OrderModel.collection.updateOne(...)` (the raw driver) to actually change it.

**Populated buyer/seller references (Phase 17, 2026-08-21):** `Order.buyer` and `items[].seller` are now populated — `{ _id, firstName, lastName, email }` and `{ _id, organizationName }` respectively — everywhere an Order is returned to a client: `GET /v1/admin/orders`, `GET /v1/orders` (buyer's own), `GET /v1/orders/:orderNumber` (all three audiences), `GET /v1/orders/seller/incoming`, `GET /v1/orders/checkout/:checkoutReference`, and the cancel/confirm-delivery/seller-status-transition responses (which return the same `Order` shape). One `ORDER_POPULATE` constant in `OrderRepository`, applied via `.populate()` on `findByOrderNumber`, `findByCheckoutReference`, `updateByOrderNumber`, and the shared private `paginate()` helper (covers `findByBuyer`/`findBySeller`/`findAllAdmin` in one place) — not a special admin-only version.
- **Deliberately NOT populated:** `OrderRepository.findByIds` — used internally only by `PaymentService`'s webhook/email flow (`sendOrderEmails` groups orders by `item.seller.toString()` against a raw ObjectId; populating there would silently break that grouping for zero benefit, since confirmation emails never display buyer/seller objects). Also not populated: `create` (checkout's own response — the buyer just authenticated as themselves, so populating adds no information; fetch `GET /v1/orders/:orderNumber` afterward for the populated shape), `findStalePendingOrders`/`findRecent`/`expireIfPending` (the auto-expiry job and dashboard activity feed never read these fields).
- **Real regression fixed as part of this phase, not just audited:** four internal ownership checks in `OrderService` (`getOwnedOrderForBuyer`, `updateStatusAsSeller`'s `ownsItem` check, `getByCheckoutReference`'s `isOwner` check, `getOrderDetail`'s `isBuyer`/`isSeller` checks) previously did `order.buyer.toString() === id`, which silently breaks once the field is populated (`.toString()` on a populated Mongoose document falls back to `Object.prototype.toString`, never equal to anything). Fixed with a small `refId()` helper that extracts the underlying `Types.ObjectId` whether the field arrived populated or raw, then compares via `.equals()`. Verified for real (not just reasoned about): a buyer other than the owner gets 404 from cancel/confirm-delivery (ownership is structural, matching the existing addresses-domain convention) and 403 from the detail endpoint; a seller with no item on the order gets 403 from both detail and status-update.

## Campaigns + Donations + CampaignFund (Phase 12, fully built, tested end-to-end against staging Mongo+Redis+real Paystack test-mode API)

First real functionality for Campaign Org accounts (`ngo`/`foundation`/`religious_body`/`agency`) beyond login + document management. Reuses Phase 11's payment infrastructure directly — same `PaymentGateway`, same `PaymentService`, same `/v1/webhooks/paystack` endpoint, just a new `transactionType` branch — not a second payment pipeline.

**Restricted funds — the non-negotiable part (BACKEND_RULES.md §20):** `CampaignFund.canWithdrawCash` (default `false`) and `CampaignFund.isRestricted` (default `true`) are schema-level `immutable: true` in `campaign-fund.model.ts` — not "default false and hope nothing changes it." This was asserted programmatically in the test run (checked actual response keys against a `/cash|withdraw|bank/i` pattern), not eyeballed. Any future change to this method's return shape must be checked against the same rule.

**One Campaign, one CampaignFund, created together:** `CampaignService.create` creates the `Campaign` (`status: pending_approval`) then immediately calls `CampaignFundService.createFundForCampaign` (idempotent — no-op if a fund already exists for that campaign). `availableBalance` is never set directly by any caller — it's recalculated in a `pre('save')` hook (`totalDonated - totalAllocatedToFood`) every time the fund document is saved, which is why `CampaignFundRepository.recordDonation` fetches-then-`.save()`s rather than using an atomic `findOneAndUpdate` (an atomic update would skip document middleware and never trigger the hook).

**Fund mutation is its own transaction, mirroring Phase 11.5's checkout pattern exactly:** `CampaignFundService.recordDonation` wraps the `CampaignFund` update (push donation, increment `totalDonated`, append `auditTrail` entry) and the `Campaign` update (`$inc currentFunding`/`donorCount`, via `CampaignRepository.incrementFunding`) in one `mongoose.startSession()` + `session.withTransaction()` — two different documents, one atomic unit, same reasoning as checkout's stock-decrement-plus-order-creation transaction.

**Payment integration (`PaymentService`):** `initializeDonationPayment(donorId, donorEmail, campaignId, amount)` validates the campaign is `status: active` and `amount >= DONATION_MINIMUM_KOBO` (₦500, `src/utils/constants.ts`) **before** ever calling Paystack — verified in the test run that a below-minimum donation attempt created zero `Transaction` records. `processSuccessfulPayment`/`processFailedPayment` both branch on `transaction.transactionType` right after their existing atomic idempotency-claim step; the `product_purchase` branch is untouched. On success, `recordDonation` runs, then a donor confirmation email (impact message: `floor(amount / 500)` meals, via `MEAL_COST_NGN` in `constants.ts` — the same constant `CampaignFundService`'s `mealsEquivalent` uses, so the two can't drift apart) and an org notification email are sent, both wrapped in try/catch (payment already succeeded — an email failure must never look like a payment failure, same pattern as order confirmation emails). On failure, nothing is restored (a donation never touches stock or a cart, and nothing was ever added to the fund pre-confirmation) — just a donor notification.

**Deviation from TASKS.md's own scope note 4:** the task doc claimed `TransactionType` already had `'campaign_donation'` as an unused placeholder value. It didn't — the enum only had `product_purchase`. Added `CAMPAIGN_DONATION = 'campaign_donation'` as part of this phase (additive, nothing existing changed) since the rest of the payment-integration work depends on it existing.

**`GET /v1/campaigns/:id` needed optional auth, which didn't exist yet:** the spec wanted this public detail endpoint to show any status to the owning org or an admin, active-only to everyone else — on the *same* route, not a separate protected one. New `optionalAuth` middleware (`protect.middleware.ts`) does the same token-verification/identity-resolution as `protect`, but a missing/invalid/expired token just leaves the request anonymous instead of throwing 401. Reused, not duplicated, logic — only the failure behavior differs.

**Public browse (`CampaignRepository.findPublic`) sorts by urgency then recency**, which plain `.find().sort()` can't express (no native concept of a custom enum priority order) — uses an aggregation pipeline (`$addFields` a computed `urgencyRank` via `$switch`, sort on that, then `$lookup` the organization) instead, same reasoning as `ProductRepository.findMany`'s Phase 11.5 deactivated-seller exclusion: whatever shapes the result set has to happen before `$skip`/`$limit` or pagination math goes wrong. Aggregation results are plain objects, not Mongoose documents — `CampaignService`'s `addComputedFields` helper is written to accept either (a real document already `.toObject()`'d, or an aggregation-pipeline plain object) since `getById` uses the former and `browse` uses the latter.

**Campaign update endpoint scope, matching Product's PUT precedent:** `PUT /v1/campaigns/:id` is plain JSON (not multipart) and only accepts `description`, `distributionPlan`, `urgencyLevel`, `fundingGoal` — no image replacement, same "not built yet" gap `ProductService.updateProduct` already has, not a new inconsistency. `fundingGoal` is rejected with 400 once `Campaign.currentFunding > 0` (protects donors from goal manipulation after money has already come in) — verified both directions in the test run (allowed at 0, blocked after a donation).

**`postUpdate` sends no donor emails, on purpose** (scope decision 2 — the full Notification domain doesn't exist yet, and looping over every past donor synchronously would be both premature and the wrong pattern for when that domain does get built).

**New `ErrorCode`s:** `CAMPAIGN_ORGANIZATION_REQUIRED`, `CAMPAIGN_NOT_FOUND`, `CAMPAIGN_NOT_ACTIVE`. Fund-related validation (below-minimum donation, `fundingGoal` locked, dates invalid, title/description length) reuses the existing `VALIDATION_ERROR`, consistent with how every other domain in this codebase avoids inventing a new code per conceptually-identical case.

**Admin review** (`AdminService.listCampaigns`/`reviewCampaign`, added to the existing `AdminService` rather than a new service — mirrors `listOrganizations`/`reviewOrganization` in the same file exactly): `GET /v1/admin/campaigns` (status filter, default `pending_approval`, no pagination — same as the organizations listing), `PUT /v1/admin/campaigns/:id/approve` (`{ decision, rejectionReason? }`, required when rejecting, Brevo email either way, `409` if the campaign has already been reviewed).

**Deferred (explicitly out of scope this phase, not silently dropped):** converting campaign funds into real procurement orders (needs admin tooling that doesn't exist), mass donor emails on campaign updates (needs the Notification domain / a job queue), refunds for failed/undeliverable donations (Epic 5/Disputes territory, same boundary as Orders' post-payment cancel).

## Dashboard Stats + Donation History (Phase 13, fully built, tested end-to-end against staging Mongo+Redis, including real HTTP requests against the running app for the access-control checks)

Replaces the Phase 6 placeholder `GET /v1/organizations/dashboard` (which existed only to prove `requireVerifiedOrganization` worked and was deliberately reachable by any role) with real stats. Same route, no second dashboard endpoint added.

**Deliberate tightening, not a regression:** the route now runs `requireRole(UserRole.ORGANIZATION)` ahead of `requireVerifiedOrganization` — the Phase 6 placeholder was intentionally reachable by `user`/`admin`/`fso` roles too; real stats logic doesn't make sense for a non-organization account, so that's now blocked with `403 FORBIDDEN`. Verified this is the only thing that changed: an unverified organization still gets the exact same `403 ORGANIZATION_NOT_VERIFIED` as before.

**One endpoint, two response shapes**, a discriminated union on `category` (`SupplyDashboardStats | CampaignDashboardStats`, `src/services/organization.service.ts`) — branches via the existing `getOrgDocumentCategory()` from Phase 5's `document-catalog.ts`, no second farmer/vendor-vs-ngo classifier written.

**Exact definitions — don't redefine these differently later:**
- **`revenue` (supply-side) = `$sum: '$subtotal'` across the org's `paymentStatus: completed` orders, NOT `total`.** Deliberately excludes `deliveryFee` — that's not product revenue, and there's no payout/logistics-split system yet to justify folding it in. `OrderRepository.getSellerStats` does this as a single match+group aggregation (each Order already belongs to exactly one seller from Phase 11's per-seller split, so no per-item unwind is needed).
- **`totalRaised` (campaign-side) = `$sum` of `Campaign.currentFunding`** across the org's campaigns — reads the already-denormalized field, never re-touches the more sensitive `CampaignFund` model for this aggregate.
- **`familiesReached` (campaign-side) = `$sum` of `beneficiaries`** across every `distributionRecords` entry on **all** of the org's campaigns, active or not — `CampaignRepository.getOrganizationStats` computes this and `activeCampaigns`/`totalRaised` in one aggregation via `$facet` (two independent sub-pipelines so unwinding `distributionRecords` for the beneficiary sum can't multiply/corrupt the campaign-level counts in the same pass).
- **`totalProducts` (supply-side) = count of the seller's currently-`isActive: true` products only** — soft-deleted listings don't count toward "my current product count."

**Bundled alongside this phase (small, directly related — not a separate phase):** `GET /v1/users/donations` gives an individual donor their own donation history, which nothing built in Phase 12 exposed (that phase's `GET /campaigns/:id/donations` is org-facing and donor-*sanitized*, the opposite need). New `TransactionRepository.findByPayer` (paginated, `relatedCampaign` populated one level deep for `title`, populated one level further for the org's `organizationName`) and a new small `DonationService` (`src/services/donation.service.ts`, kept out of `UserService` — this isn't about the user record) backing it. Includes `pending`/`failed` attempts, not just `completed` ones, so a donor can see a payment that didn't go through, not just successful ones. No role restriction — any authenticated account (including an organization) can have donated.

## Admin API Surface (Phase 15, fully built, tested end-to-end against staging Mongo+Redis via real HTTP requests)

Closes the backend gaps standing between now and scaffolding the separate admin web dashboard repo. Organizations and Campaigns admin endpoints already existed (Phases 5.5–5.8, 12) and were untouched — this phase adds the three genuinely missing pieces (Users, Orders, Products admin-wide visibility) plus one platform-wide Dashboard stats endpoint, all under the existing `/v1/admin` router (`requireRole(ADMIN)` already applied at the router level).

- **`GET /v1/admin/users`** — filter by `role`/`isActive`, free-text `search` across `email`/`firstName`/`lastName`/`organizationName` (case-insensitive regex), paginated. `PUT /v1/admin/users/:id/status` (`{ isActive: boolean }`) is a status toggle on the existing `isActive` field, not a new status system — deactivating only blocks future login (reuses `AuthService.login`'s existing check untouched) and never touches historical orders/campaigns/products.
- **`GET /v1/admin/orders`** — no buyer/seller restriction, unlike the existing buyer-scoped/seller-scoped listings. Single-order detail already worked via the existing `GET /v1/orders/:orderNumber` (admin-permitted since Phase 11) — this phase only added the missing LIST endpoint.
- **`GET /v1/admin/products`** — filter by `isActive`/`isApproved`/`category`/`sellerId`, paginated. Deliberately bypasses the `isActive`/deactivated-seller filtering `ProductRepository.findMany` applies for public browsing (Phase 11.5.3) — admin needs to see everything, including inactive products and products belonging to deactivated organizations. Read visibility only this phase — no product moderation (approve/reject) yet; `isApproved` is still hardcoded `true` at creation per Phase 8's own `// TODO: v1.1`.
- **`GET /v1/admin/dashboard`** — platform-wide, distinct from Phase 13's `GET /v1/organizations/dashboard` (per-organization, org-facing). Returns `{ users: { total, byRole }, orders: { total, revenue }, campaigns: { active, totalDonated }, pendingVerifications, recentActivity }`. All independent aggregates run via `Promise.all`, not sequential awaits. `orders.revenue` is the same definition as Phase 13 (sum of `subtotal`, never `total`/`deliveryFee`, across `paymentStatus: completed` orders only) — `OrderRepository.getOrderStats` computes `total` (count of ALL orders, any status) and `revenue` in one `$facet` aggregation. `campaigns.totalDonated` sums `Campaign.currentFunding` across every campaign platform-wide (not org-scoped) — same denormalized-field reasoning as Phase 13, never re-touches `CampaignFund` for this aggregate. `pendingVerifications` counts orgs with `verificationStatus` in `pending`/`under_review`. `recentActivity` merges the last 10 orders + last 10 campaign submissions (`OrderRepository.findRecent`/`CampaignRepository.findRecent`) into one feed sorted by `createdAt` descending, capped at 10 — built in `AdminService`, not a single-collection aggregation, since it spans two collections.
- `AdminService` gained two new constructor dependencies (`ProductRepository`, `OrderRepository`) — `service-container.ts` had to reorder `productRepository`/`orderRepository`'s instantiation to before `adminService`'s (both are dependency-free, so this was a safe move, not a behavior change).

**Bug caught by this phase's own test pass, fixed before being called done:** `OrderRepository.findAllAdmin`'s first draft passed the `{ orderStatus?, paymentStatus? }` filter straight into `OrderModel.find()`. With no query params, that filter is `{ orderStatus: undefined, paymentStatus: undefined }` — and the MongoDB driver does NOT drop `undefined`-valued keys, it BSON-serializes them to `{ orderStatus: null }`, which matches nothing (no real order ever has a null status). `GET /v1/admin/orders` with no filters was silently returning an empty list. Fixed by building the query conditionally, matching the pattern `ProductRepository.findManyAdmin`/`UserRepository.findMany` already used correctly. Worth remembering for any future "optional filter object" endpoint in this codebase — don't spread a filter object with possibly-`undefined` values directly into a Mongo query.

## Pagination Standardization (Phase 16, fully built, tested end-to-end against staging Mongo+Redis via real HTTP requests)

Closed a real gap the admin dashboard build surfaced: `GET /v1/admin/organizations` (built Phase 5.5–5.8, before `pagination.ts` existed as of Phase 8) still returned an unbounded plain array. Full audit run across every `GET` list-style endpoint in the codebase, not just the known offender — two more gaps found and fixed with the exact same pattern (`parsePagination`/`buildPaginationMeta`, default `limit: 20`, max `limit: 50`).

**Fixed (previously unpaginated, now paginated):**
- `GET /v1/admin/organizations` — was a plain array; now `{ status, message, data: { data: [...orgs], meta } }` (the literal shape named in the task spec — note the doubly-nested `data` key, kept distinct from the sibling admin endpoints below which use a domain-named key instead).
- `GET /v1/admin/campaigns` — `AdminService.listCampaigns`/`CampaignRepository.findByStatus` mirrored `listOrganizations`/`findOrganizations`'s unpaginated shape exactly (same origin, same bug); fixed the same way. Response: `{ campaigns: [...], meta }`.
- `GET /v1/campaigns/:id/donations` — `CampaignFundService.getSanitizedDonations` returned the entire `CampaignFund.donations` array with no bound at all. A popular campaign's donor list has no upper limit, unlike e.g. delivery addresses (hard-capped at 5) — this one was a genuine correctness gap, not just a style inconsistency. Since `donations` is an embedded subdocument array on a single `CampaignFund` document rather than a separate collection, pagination is applied **in-memory** after fetching the one document and sorting most-recent-first (not an aggregation `$unwind`/`$skip`/`$limit`) — there's only ever one document read either way, so the aggregation approach would add complexity without changing what's actually read from Mongo. Response: `{ donations: [...], meta }`.

**Audited and confirmed already correct (no change needed):** `GET /v1/products`, `GET /v1/orders` (buyer's own), `GET /v1/orders/seller/incoming`, `GET /v1/campaigns` (public browse), `GET /v1/users/donations`, `GET /v1/admin/users`, `GET /v1/admin/orders`, `GET /v1/admin/products`.

**Audited and confirmed intentionally NOT paginated (documented exception, structurally bounded — not drift):** `GET /v1/users/addresses` (hard business cap of 5), `GET /v1/organizations/document-catalog` (fixed ~5-entry catalog per category, static reference data), `GET /v1/organizations/verification-status` (one org's own status + own submitted documents, bounded by the catalog), `GET /v1/orders/checkout/:checkoutReference` (sibling orders from one single checkout event, bounded by how many distinct sellers were in one cart). Single-resource and aggregate-stats endpoints (`GET /v1/cart`, `GET /v1/auth/me`, `GET /v1/products/:id`, `GET /v1/campaigns/:id`, `GET /v1/campaigns/:id/fund-summary`, `GET /v1/admin/organizations/:id`, `GET /v1/organizations/dashboard`, `GET /v1/admin/dashboard`) aren't list endpoints at all and were excluded from the audit's scope on that basis.

**`?limit=100` behavior, worth remembering:** every paginated endpoint in this codebase (this phase's 3 fixes included) rejects an out-of-range `limit` with `400 VALIDATION_ERROR` via an `isInt({ min: 1, max: 50 })` express-validator rule at the route boundary — it does **not** rely on `parsePagination`'s internal `Math.min(50, ...)` clamping to silently correct it. That clamping exists as a defensive fallback for any caller that reaches the service layer without going through route validation, not as the primary enforcement mechanism. Don't add a new paginated endpoint that clamps instead of rejecting — that would be the "second pagination style" BACKEND_RULES.md's new §30.1 explicitly warns against.

**BACKEND_RULES.md updated** — new §30.1 "Pagination is Mandatory for List Endpoints" added as a standing rule: every list/collection GET endpoint must paginate via `pagination.ts`, default `limit: 20` / max `limit: 50` unless documented otherwise, with an explicit carve-out for single-resource/fixed-small-reference/aggregate-stats endpoints. This is a deliberate edit to the project's constitution file, not routine code change — flagged here for visibility.
