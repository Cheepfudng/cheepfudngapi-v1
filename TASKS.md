# TASKS — URGENT: New Products Created With Pre-Phase-19 Shape

Confirmed via direct MongoDB inspection: products created today have `isApproved: true` and no `moderationStatus` field at all — the exact opposite of what Phase 19 established (`moderationStatus: 'pending'` on creation, no `isApproved` field). This means brand-new products are invisible to both public browse and every admin tab, since both filter on `moderationStatus` existing and matching one of its 3 real values.

## Investigate — determine the actual cause before fixing anything

- [x] **Which environment created these?**

  **Finding — neither hypothesis as literally stated, but a real deployment-lag issue, confirmed:** first ruled out local `dist/` entirely — no `cheepfudngapi` `node dist/server.js` process was even running locally (checked all running `node.exe` processes on the machine by command line; the two that looked plausible from their npm script names turned out to be `expo start` and `vite`, both unrelated projects). The mobile app's actual config (`cheepfudngmobileapp/.env`, `src/constants/env.ts`, `src/api/client.ts`) confirmed it talks **only** to `EXPO_PUBLIC_API_URL=https://cheepfud-api-staging.onrender.com` — a `LOCAL_SERVER_URL` variable exists but is unused dead config (`.env.example` even comments "never to a local server"). So every real product-creation request, including the 3 bad ones, went to the **deployed Render staging service**, not anything local. Live-tested that deployed URL directly (malformed-id validation, and the 3 specific broken product IDs 404ing correctly) — it is running fully current, correct Phase-19-and-later code **right now**. Cross-referencing timestamps: the 3 bad documents were created at 04:17, 04:51, and 04:55 AM on 2026-09-10, and `origin/firstClaude` (the branch this deploys from) received a push at **05:04:45 AM** the same morning — i.e., a deploy landed shortly after all 3 bad creations and before this investigation. Conclusion: the deployed staging service was running a build that predated the Phase 19 product-moderation logic at the exact time these 3 requests were made, and was redeployed to current code minutes later (the same push/redeploy referenced by the checkout-lock task as "just found and fixed") — a **deployment-freshness gap that has already closed itself**, not an ongoing local build issue.

- [x] **Or is there a second product-creation code path?**

  **Finding — no, ruled out.** Grepped the entire `src/` tree for every way a `Product` document could be constructed: `ProductModel.create`, `Product.create`, `new ProductModel(`, and every caller of `productRepository.create`. Exactly one call site exists end to end: `ProductService.createProduct` → `ProductRepository.create` → `ProductModel.create`, wired through `service-container.ts` the same as every other domain. `src/scripts/` contains only the original Phase 19 migration script, which never creates new products (only backfills/unsets fields on existing ones). No seed script, admin utility, or leftover route exists anywhere.

- [x] Confirm which of the two (or both) actually produced the 3 affected documents. **Confirmed: deployment lag on the Render staging service, not a code-level second path — see above.**

## Fix

- [x] Ensure there is exactly ONE way to create a product with correct defaults. **Already true — no code change needed.** `ProductService.createProduct` never explicitly sets `moderationStatus` or `isApproved` at all; it relies entirely on `Product.model.ts`'s schema default (`moderationStatus: { default: ProductModerationStatus.PENDING }`, `isApproved` not declared in the schema at all since Phase 19). Verified this current source is exactly what's now live on the deployed staging service the mobile app actually uses (see below).
- [x] **Retroactively fixed the 3 affected documents** — same approach as Phase 19's original migration: `moderationStatus: 'approved'` set from the existing `isApproved: true` (matching how pre-Phase-19 products were grandfathered in as already-approved, since they were created under the old auto-approve rule), then `isApproved` unset via the raw driver (still required, same schema-strict-casting gotcha as the original migration — `Model.updateMany()` silently drops `$unset` on fields no longer declared in the schema).
- [x] Created a genuinely fresh test product through the real path — **against the actual live deployed staging service** (not just local source), since that's the system mobile really hits and the whole point was to confirm what mobile experiences now. Confirmed `.env`/`.env.staging` share the same `MONGODB_URI`/`REDIS_URL`/`JWT_SECRET`, so a token minted locally authenticated successfully against the live deployment.

## Test

- [x] Fresh product creation (against the live deployed service) → `moderationStatus: 'pending'`, no `isApproved` field, does NOT appear in public browse or the public detail endpoint until approved — all confirmed via real HTTP responses from `https://cheepfud-api-staging.onrender.com`, not simulated.
- [x] The 3 previously-broken products → now have `moderationStatus: 'approved'` (matching their prior `isApproved: true`) and no stray `isApproved` field — confirmed via a direct raw-driver query showing zero documents left in the old shape.
- [x] Confirmed no other product-related endpoint is affected: the deployed service's list/detail/moderate logic all already correctly branch on `moderationStatus` (this was never broken — only the 3 documents' *data* was stale, not the code reading them), verified by the 3 IDs already 404ing correctly pre-fix and the fresh product's list/detail behavior post-fix.

**Verified via two throwaway scripts** — one direct raw-driver inspection against Mongo (confirming the exact 3 affected documents and their timestamps), one combined migration-fix + live-deployment verification (6 assertions, all passing, hitting the real `cheepfud-api-staging.onrender.com` for the create/list/detail calls). Both deleted after the run. `npx tsc --noEmit` clean (no source changes were needed), no stray files.

**Answer to "which hypothesis was true":** neither exactly as framed — it wasn't a stale local `dist/` build (no such process was running; local dev in this project has never run from `dist/`) and it wasn't a second code path (confirmed there is only ever one). It was **the deployed Render staging service itself lagging behind the pushed `firstClaude` branch** at the specific moment these 3 requests landed, self-resolved by a redeploy minutes later. Worth flagging as a process gap, not a code gap: there's currently no way to know from inside this repo when Render last redeployed relative to the latest push, so a period like this — real user traffic hitting an old deployed revision — could recur silently around any future push/deploy gap. Not fixed as part of this task (out of scope — it's a deployment/ops concern, not a code change), but flagged here for whoever owns the Render project to consider (e.g., a deployed `/version` or `/health` endpoint reporting the running commit SHA would make a future recurrence immediately diagnosable instead of requiring this kind of forensic reconstruction).
