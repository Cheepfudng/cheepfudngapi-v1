# TASKS — Extend Checkout Lock to Cover the Whole Payment Attempt

Confirmed: Phase 11.5's Redis lock correctly prevents true concurrent double-checkout, but is released immediately once `checkout()` returns — so a _sequential_ second checkout on the same still-populated cart (the cart deliberately isn't cleared until payment confirms) creates a genuine second real order. This was flagged as a known "adjacent risk" at Phase 11.5 and deferred; it's real and now needs fixing, since mobile Checkout shipping makes this a realistic, common scenario (a user reaching Paystack's page, backing out, retrying minutes later), not just a theoretical race.

## Fix

- [x] Change the checkout lock's lifecycle: instead of releasing in `checkout()`'s own `finally` immediately after the order is created and `paymentUrl` returned, **keep it held** for the duration of the payment attempt. Release it in these cases, and only these:
  - [x] The webhook confirms successful payment (`processSuccessfulPayment`) — release once the order transitions to `paymentStatus: completed`.
  - [x] The webhook confirms failed payment (`processFailedPayment`) — release once the order transitions to `paymentStatus: failed`.
  - [x] The buyer explicitly cancels the still-unpaid order via the existing `POST /v1/orders/:orderNumber/cancel` — release immediately, so a genuine change-of-mind doesn't force the buyer to wait out a timeout before trying again.
  - [x] A reasonable timeout elapses — 15 minutes (`CHECKOUT_LOCK_TTL_SECONDS = 15 * 60`), comfortably under the 30-minute `ORDER_EXPIRY_MINUTES` default so the lock is never still held once the order itself has already been auto-expired and its stock released. Enforced via the Redis key's own `EX` TTL, not a separate manual check.
- [x] The paths that already correctly release the lock immediately — a stock-shortage rejection, or a Paystack-init failure inside `checkout()` itself — are unaffected. Verified unaffected by test, not just by inspection.
- [x] Genuinely failed/errored `checkout()` calls never acquire a lasting lock — a `retainLockForPayment` flag (default `false`) is only flipped `true` immediately before the success return, right after a real `paymentUrl` comes back from Paystack; every other path (thrown before that point, or the Paystack-init catch block) falls through to the outer `finally` with the flag still `false` and releases immediately.

**Implementation:** new `CheckoutLockService` (`src/services/checkout-lock.service.ts`) owns the lock as a domain concept — its key shape, its 15-minute TTL, and the decision to use the **`checkoutReference` itself as the lock token** (rather than a random UUID `RedisLock` generates by default). That's what makes release-from-elsewhere safe: a webhook or a cancel for checkout A presents A's reference, so `RedisLock`'s existing compare-and-delete (already correct, unchanged) refuses to release a lock a *newer* checkout B has since taken — a late webhook for an abandoned checkout can never unlock a fresh one. `RedisLock.acquire()` gained an optional third `token` parameter (defaults to `randomUUID()`, its original behavior) to allow this. `OrderService.checkout()` now generates `checkoutReference` up front (it doubles as the lock token, so the lock has to exist before any order does) instead of inside the transaction. `PaymentService` gained a `CheckoutLockService` dependency, releasing in `processSuccessfulPayment` (after orders flip to `completed`, deliberately not on the earlier amount-mismatch path where money is in limbo pending manual review) and `processFailedPayment` (after stock restore + orders flip to `cancelled`). `OrderService.cancel()` releases via the order's own `checkoutReference` and buyer id (using the existing `refId()` helper, since `order.buyer` may already be populated).

## Test

- [x] Sequential double-checkout on the same still-populated cart → second attempt now correctly gets `409`, not a second real order.
- [x] Complete a real payment (simulated by calling `PaymentService.processSuccessfulPayment` directly with a matching-amount payload, equivalent to what a signed webhook delivers) → lock releases, a fresh checkout on a refilled cart succeeds immediately afterward.
- [x] Simulate a failed payment (`processFailedPayment`) → lock releases the same way; retrying checkout on the same (stock-restored, still-populated) cart succeeds immediately.
- [x] Explicitly cancel a pending unpaid order → lock releases immediately (verified: a checkout attempted *before* the cancel still correctly gets `409`; one attempted immediately *after* succeeds with no wait).
- [x] Lock TTL mechanism verified directly (a real 15-minute wait isn't practical in an automated test): confirmed the Redis key's stored value is the checkoutReference and its TTL is ~900s (897s observed) immediately after acquisition — the natural-expiry mechanism is correctly wired, it will release itself with no external action needed.
- [x] Regression: true concurrent (`Promise.all`) double-checkout still produces exactly one `201` + one `409`, exactly one order in Mongo.
- [x] Regression: a genuinely failed checkout attempt (stock shortage) still releases its lock immediately and does not block a subsequent legitimate attempt — verified as its own scenario, and incidentally reconfirmed a second time when a real transient Paystack connection reset (`ECONNRESET`) hit during testing: that Paystack-init-failure path also released its lock immediately, exactly as designed.

**Verified via three throwaway HTTP-level integration scripts against staging Mongo+Redis+real Paystack test-mode API** (split across separate process runs to stay under the pre-existing, unrelated `checkoutLimiter` of 10 requests/15min/IP — an in-memory-store limiter, so a fresh process resets its counter) — 12 assertions across the 7 scenarios above, all passing; scripts deleted after the run. `npx tsc --noEmit` clean throughout, no stray files left behind.
